# Release 3.5.2d: synchronous CF and 640-byte task stacks tested

29 September 2026. Evidence: user photos 25851–25855 and the follow-up
confirmation, “Everything seems to work as outlined, screenshots attached”.
The outlined tests covered keyboard, zoom/panning, normal screen speed,
busy-loop Ctrl-C, CF scratch-file write/sync/readback, reboot persistence,
and deletion/sync. Functional success is user-reported; the photos directly
show the boot, shell, loop commands, scratch-file directory entry, cleanup
commands, and stack/memory readings. The file-content readback itself is not
visible in these photos, so persistence success relies on the user's report.

## Observed readings

| Photo / point in test | Task samples / calls | Task written peak | Shared samples / calls | Shared written peak |
| --- | ---: | ---: | ---: | ---: |
| 25851: initial boot and meminfo -s | 1 / 1 | 82 / 640 | 77 / 2,457 | 222 / 1,024 |
| 25852: after first busy loop | 930 / 930 | 202 / 640 | 276 / 8,826 | 222 / 1,024 |
| 25854: after reboot and another loop | 578 / 578 | 202 / 640 | 228 / 7,288 | 222 / 1,024 |
| 25855: final reading after cleanup | 595 / 595 | 202 / 640 | 323 / 10,305 | 222 / 1,024 |

All these readings have task/shared guard flags zero, `unknown=0`, and
`sample=all/32 guard=each`. Counts restart after reboot; the rows must not be
summed as independent measurements. The final photo also contains an earlier
reading from the same boot, repeated from photo 25854.

The task written peak matches 3.5.2c's 202 bytes with the smaller task stack.
The observed shared peak is 222 bytes versus 224 in the longer 3.5.2c run.
These measurements are workload evidence, not an absolute maximum or a ROM-only
stack specification. Shared depths are sampled; guards and written watermarks
retain the limitations described in the release notes.

The TASK heap row is **13,574 bytes**, versus 14,534 with the preceding
700-byte/16-slot layout: a **960-byte reduction**, matching 60 bytes per slot.
The final memory summary remains **Main 79/455K used, 376K free; XMS 0/0K used**.
Do not infer a 1 KiB increase in conventional free RAM from this rounded output.
`meminfo -s` filters the heap rows, so `Total mem 0` and the filtered Heap/free
subtotals are not whole-system memory totals. Keep using `-s` with this older
CF userland; full process listings and `ps` need matching rebuilt tools.

Photo 25853 shows the HPR352D boot, stacks=640/1024, one block request header,
Minix root on `/dev/cfa1`, and a usable shell. Subsequent photos show the
scratch file present after reboot and the cleanup `rm`/`sync` commands.
The malformed loop in 25854 and misspelled meminfo command in 25855 produce
normal shell errors; corrected commands work afterward. The boot also retains
the previously observed unchecked-Minix-filesystem warning. This small
persistence test does not establish filesystem-wide integrity or constitute
an fsck result.

## Outcome

The requested 3.5.2d hardware test passed as reported: synchronous ATA-CF,
640-byte task stacks, the existing ROM bridge and BIOS console remained usable
through the listed controls, loop, reboot and small file operations. No guard
failure or rejected stack bounds appeared. Keep this configuration for the next
investigation; broader kernel/interrupt-stack tracing is still outstanding.

This is an evidence/documentation update only. K352D remains 62,472 bytes,
SHA-256 `1f3e0021103d191c6447f79c38106a77f022b49dc252fda2cb99fa3b9d752a42`.
Release tags, ZIPs, source-kit build-time validation and binaries are unchanged.
3.5.2d remains a diagnostic prerelease; stable 3.5 remains stable.
