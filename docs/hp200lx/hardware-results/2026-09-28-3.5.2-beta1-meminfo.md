# Release 3.5.2 beta 1: initial stack measurements and output slowdown

28 September 2026. Evidence: user-supplied photograph `25821.jpg` and the
accompanying report: keyboard, zoom and panning work; screen printing is much
slower than prior versions, described as resembling a typewriter.

The user is testing the 3.5.2 beta 1 supplied in the preceding release handoff.
The photograph shows the new HPST diagnostics, meminfo output and a shell prompt;
it does not show the boot banner or HPBOOT relocation line.

| Peak written depth (`used`) | 80 / 700 bytes | 282 / 1,024 bytes |
| Peak ROM-region written depth (`rom`) | 46 bytes | 168 bytes |
| Guard flags | 0 | 0 |
| Samples | Nonzero | Nonzero |

`unknown=0`. Both stack paths were sampled, with no reported guard corruption
or rejected bounds. The task sample count appears as 7; the shared count is not
needed for this conclusion and is not transcribed here. Counts alone do not
establish test duration or worst-case workload coverage.

Memory summary: **Main 79/453K used, 374K free; XMS 0/0K used, 0K free**.
These are the displayed meminfo figures, rounded by the utility. This is not a
matched workload comparison against 3.5.1; the process/heap listing includes the
shell and meminfo itself. XMS remains disabled, so these figures do not represent
all of the palmtop's installed RAM.

The reported depths include the six-byte probe metadata and existing bridge/
interrupt overhead in `used`. The `rom` field includes the fake interrupt frame
and any nested work on that stack. Peaks can come from different calls.
Written watermarks miss untouched stack allocations, marker-value writes and
firmware execution on a different SS. These results provide no observed need
for 1 KiB in this run, but do not justify declaring 512 bytes universally safe
or reducing the 700-byte task stack. CPU-bound user-mode stress, longer runs,
modifier/repeat and Ctrl-C testing have not been reported for this run.

## Reported performance regression

Screen output is noticeably slower than earlier versions. The leading source-
based explanation is diagnostic overhead: every measured ROM IRQ2 call paints
unused stack words with `rep stosw`, then scans upward from the lower bound
word by word after ROM returns. Both loops run with maskable interrupts disabled.
This costs CPU time and interrupt latency even when stack use is shallow.
The normal console driver was not changed by the beta's diagnostic patch.

This is a hypothesis supported by the code, not a measured attribution. No
controlled on/off comparison, interrupt-rate measurement or timing trace has
been supplied. The slowdown must not be described as fixed, nor should this
run's timing be assumed representative of the uninstrumented kernel.

The next diagnostic revision should reduce painting/scanning frequency or
provide a bounded collection window, retain separate coverage counters and
sticky guard checks, then compare screen output with the probe inactive and
active on the same build. Less frequent sampling must be documented as potentially
missing rare peaks; keeping the current stack sizes avoids mixing a stack-size
experiment with that performance comparison.

Use the hardware-tested 3.5.1 beta or stable 3.5 for normal use. This update
records evidence only; it does not replace a kernel, helper, release tag or ZIP.
The original downloadable source kit retains its build-time pending status;
these living notes record the later hardware report.
