# Release 3.5.2b: faster screen output and sampled stack results

28 September 2026. Evidence: user photograph `25823.jpg` and report,
"Screen output is faster again". This is a qualitative hardware improvement,
not a timed benchmark or confirmation of exact parity with older releases.
The photo shows meminfo, all four HPST lines and a shell prompt. It does not
show the boot banner/HPBOOT line or establish a fresh keyboard/zoom/panning
stress test for this run.

| Measurement | Task kernel stack | Shared interrupt stack |
| --- | ---: | ---: |
| Measured samples (`n`) | 1 | 128 |
| Total valid calls | 16 | 4,082 |
| Sampled written peak (`used`) | 82 / 700 bytes | 222 / 1,024 bytes |
| Sampled ROM-region peak (`rom`) | 48 bytes | 132 bytes |
| Sticky guard flags | 0 | 0 |

The report shows `sample=1/32 guard=each` and `unknown=0`. Sample counts match
the implemented cadence: first call, then calls 33, 65, etc. Sixteen task calls
yield one sample; 4,082 shared calls yield 128 samples. Both paths have measured
coverage, but task coverage is still especially limited.

Memory summary: **Main 79/455K used, 376K free; XMS 0/0K used, 0K free**.
This is the displayed utility summary. It is not a controlled memory-saving
comparison with photo 25821; process/heap state and layout can differ.

Reducing watermark frequency is followed by user-reported faster output,
which supports diagnostic overhead as the earlier slowdown's cause. It does
not provide an IRQ-rate measurement or quantify remaining overhead. This build
still performs bounds/guard checks on valid calls and scans on sampled calls.

The previous full-probe beta recorded task/shared peaks 80/700 and 282/1,024.
The new shared peak of 222 does not demonstrate reduced ROM demand: sampling
can miss rare paths, and the workloads are not controlled. Guard checks cover
valid calls even when their depths are not sampled, but cannot detect every
possible overwrite. Watermarks measure written locations, not all SP movement.
Neither run establishes worst-case safety or a reason to reduce stack sizes.

Next useful evidence: a longer normal-use run, keyboard/zoom/panning checks,
a CPU-bound user loop with Ctrl-C, then another meminfo photo. Look for growing
sample counts on both stacks and unchanged zero guard/unknown fields. Any
nonzero guard/unknown should be photographed and followed by a return to the
working fallback before further stress testing.

The earlier photo 25822 showed a DOS installation path mismatch: files were
copied into `C:\ELKS352` while RUN352B requires `C:\ELKS352B`. It was a launcher
preflight failure before ELKS started, not a kernel boot failure. Photo 25823
shows the subsequent successful diagnostic session.

This update records evidence only. The kernel, tag, helpers and ZIPs remain
unchanged; their bundled notes retain the build-time pending status. Stable
3.5 remains stable; 3.5.2b remains a diagnostic prerelease.
